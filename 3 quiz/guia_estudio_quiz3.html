Clase 15Índices

Conceptos clave

Índice: estructura de datos que permite agilizar las consultas evitando la lectura de datos innecesarios. Generalmente son árboles B+. "Agilizar" no significa "hacer magia".
Cardinalidad: cantidad de valores distintos en un conjunto (o también, cuántas veces aparece un valor en un conjunto).
Selectividad: indica qué tanto se puede reducir la cantidad de registros a buscar dependiendo de una condición.
  • ✅ De 100'000.000 a 1 → where person_id = '123' (excelente)
  • ➖ De 100'000.000 a 50'000.000 → where gender = 'FEMALE' (regular)
  • ❌ De 100'000.000 a 99'000.000 → where age between 1 and 90 (inútil)
Full scan: recorrer la tabla entera para encontrar los registros que coinciden con una condición. En tablas pequeñas no importa; en tablas grandes destruye el rendimiento (CPU, disco, contención en capas superiores). Es "uno de los peores enemigos del rendimiento". Se evita con (1) índices correctos y (2) filtros bien hechos en el where.

Analogía del libro: buscar página por página = full scan; leer la tabla de contenido e ir directo = uso de índice. Pero en una revista de 10 páginas el índice agrega complejidad sin ganar velocidad → en tablas pequeñas no vale la pena.

Tamaños orientativos: ~1.000 registros = muy pequeña; cientos de miles = mediana; decenas de millones = grande.

Índice normal vs índice invertido

-- Índice "normal": lugar del valor completo
SELENA GOMEZ ........ 1
BECKY G ............. 2
KAROL G ............. 3
SELENA QUINTANILLA .. 4
-- Índice invertido: lugar de cada PALABRA
SELENA ........ [1, 4]
GOMEZ ......... [1]
BECKY ......... [2]
G ............. [2, 3]
QUINTANILLA ... [4]

El invertido se usa para textos largos (Elasticsearch, motores de búsqueda web). En MariaDB es lo que hay detrás de FULLTEXT.

Índices de 1 nivel vs "n" niveles (compuestos)

Con where genre='female' and id_type='CC' sobre una tabla 50/50: un índice solo por genre descarta el 50%. Un índice multinivel (genre, id_type) hace doble filtro: omite male y también los id_type <> 'CC'.

En los índices multinivel el orden importa, y mucho. Un índice (last_name, first_name) sirve para filtrar por last_name o por last_name + first_name, pero no para filtrar solo por first_name (regla del prefijo izquierdo).

¿Qué tener en cuenta?

  • Consulta más rápida → escritura más lenta: insert/update/delete pueden implicar rebalanceo de árboles.
  • No todo es candidato a indexar: solo los campos que lo necesiten.
  • LIKE puede anular el índice: like 'A%' → usa índice · like '%A' → no usa · like '%A%' → no usa
  • MariaDB permite crear varios índices sobre el mismo campo: impacta el rendimiento y no mejora nada.
  • Si no se especifica using, PK/unique/plain son BTREE por defecto. FULLTEXT no lleva using (usa índice invertido).

Sintaxis (7 opciones de la diapositiva)

-- Op 1: plano btree sobre tabla existente (3 formas equivalentes)
alter table singers add index (first_name) using btree;
alter table singers add index idx_sing_fina(first_name) using btree;
create index idx_sing_fina on singers(first_name) using btree;

-- Op 2: único
alter table singers add unique index idx_sing_fina(first_name) using btree;
create unique index idx_sing_fina on singers(first_name) using btree;

-- Op 3: texto completo (sin "using")
alter table singers add fulltext index idx_sing_fina(first_name);
create fulltext index idx_sing_fina on singers(first_name);

-- Op 4-7: al crear la tabla
create table singers (
  id int(11) not null,
  first_name varchar(30) not null,
  last_name  varchar(30) not null,
  primary key (id),              -- la PK ya tiene índice
  unique (first_name),           -- índice único
  fulltext (first_name),         -- índice de texto completo
  index (last_name, first_name)  -- multinivel: N1 last_name, N2 first_name
);
create index idx_sing_lana_fina on singers(last_name, first_name);

-- Borrar (por nombre del índice o del campo)
alter table singers drop index idx_sing_fina;
drop index idx_sing_fina on singers;

-- Ver índices (tipo, columnas, cardinalidad...)
show indexes from singers;
show indexes from singers where Column_name = 'id';

¿Cuál es el peor índice que se podría crear en la tabla singers? diapositiva 
| Field      | Type        | Null | Key |
| id         | int(11)     | NO   | PRI |
| id_type    | varchar(3)  | NO   | PRI |
| first_name | varchar(30) | NO   |     |
| last_name  | varchar(30) | YES  |     |
| birth_date | date        | NO   |     |
| genre      | varchar(15) | NO   | MUL |

Candidatos a "peor índice":

  • Un índice duplicado sobre id / (id, id_type): la PK ya está indexada; uno extra solo hace más lenta la escritura y no aporta nada.
  • Índice sobre genre (ya existe, marcado MUL): cardinalidad muy baja (pocos géneros musicales), selectividad mala; casi nunca evita leer gran parte de la tabla.
  • Un índice HASH sobre birth_date: las fechas se buscan por rangos y hash no soporta rangos.
  • Un UNIQUE sobre first_name: es incorrecto en lo funcional (dos cantantes pueden llamarse igual).

Respuesta corta para el examen: el de menor selectividad o el redundante (genre / duplicar la PK).

Tabla singers con 10 millones de registros: ¿vale la pena indexar cada campo? diapositiva
  • id: sí (PK, selectividad máxima).
  • full_name: sí, BTREE (permite like 'SEL%'), o FULLTEXT si se busca por palabras sueltas.
  • genre: no tiene sentido solo (4 valores → cada uno ~2.5 M filas).
  • gender: no (2 valores, filtra 50%).
  • height: solo si hay búsquedas reales por rango; en general no.

Ejercicios de clase resueltos (BD "tienda")

Usuarios 500.000, Productos 50.000, Compras 15'000.000. Los nombres de columna son supuestos; ajústalos a tu script.

Ej. 1 – Contar compras con método de pago CREDIT_CARD diapositiva 
select count(*) from compras where metodo_pago = 'CREDIT_CARD';
Sin índice → full scan de 15 M filas. Toma nota del tiempo para comparar en el Ej. 5.
Ej. 2 – Compras en 2020-10-26, 2020-05-31 y 2024-01-09 diapositiva 
-- Si fecha es DATE:
select count(*) from compras
where fecha in ('2020-10-26','2020-05-31','2024-01-09');

-- Si fecha es DATETIME: NO usar date(fecha) (anula el índice), usar rangos
select count(*) from compras
where (fecha >= '2020-10-26' and fecha < '2020-10-27')
   or (fecha >= '2020-05-31' and fecha < '2020-06-01')
   or (fecha >= '2024-01-09' and fecha < '2024-01-10');
Ej. 3 – Compras en efectivo hechas solo por mujeres diapositiva 
select count(*)
from   compras c
join   usuarios u on u.id = c.usuario_id
where  c.metodo_pago = 'CASH'
and    u.genero = 'F';
Ej. 4 – Compras de 2021 de productos Samsung y Apple diapositiva 
select count(*)
from   compras c
join   productos p on p.id = c.producto_id
where  p.marca in ('Samsung','Apple')
and    c.fecha >= '2021-01-01' and c.fecha < '2022-01-01';  -- NO year(fecha)=2021
Ej. 5 – Índice óptimo para los ejercicios 1 y 2 diapositiva
  • Ej. 1 (metodo_pago): búsqueda por valor exacto → en teoría HASH. Pero InnoDB no soporta HASH real (lo convierte silenciosamente a BTREE), así que en la práctica: create index idx_comp_mepa on compras(metodo_pago);. Ojo: baja cardinalidad (pocos métodos), así que la mejora depende de qué tan frecuente sea CREDIT_CARD. Como es un count(*), el índice además es cubriente (no necesita ir a la tabla) y por eso sí mejora bastante.
  • Ej. 2 (fecha): BTREE, porque las fechas se consultan por igualdad y por rangos. create index idx_comp_fech on compras(fecha) using btree;
Ej. 6 – Índices para los ejercicios 3 y 4 diapositiva 
-- Ej 3: filtrar compras por método y unir con usuarios
create index idx_comp_mepa_usua on compras(metodo_pago, usuario_id);
-- usuarios.id ya es PK. Índice por genero en usuarios aporta poco (2 valores).

-- Ej 4: productos por marca, y compras por producto + fecha
create index idx_prod_marc on productos(marca);
create index idx_comp_prod_fech on compras(producto_id, fecha);
Regla: indexa la clave de join del lado grande (compras) y combínala con el filtro de rango (fecha) después de la columna de igualdad.
Ej. 7 – Conclusiones diapositiva
  • Los índices bien elegidos reducen drásticamente el tiempo en tablas grandes (15 M).
  • Índices sobre columnas de baja cardinalidad mejoran poco.
  • Aplicar funciones a la columna (year(fecha), date(fecha)) impide usar el índice.
  • Crear índices tarda y hace más lentas las escrituras: indexar con sabiduría.

Práctica extra (estilo profesor)

Una tabla logs de 80 M filas se consulta con where nivel='ERROR' (5 valores posibles) y where fecha between .... ¿Qué índice crearías? extra
BTREE sobre fecha (rangos, alta cardinalidad). Si siempre se filtran juntos: compuesto (nivel, fecha) — igualdad primero, rango después. Un índice solo por nivel tiene baja selectividad.
¿Qué consultas usan el índice idx(last_name, first_name)? extra 
a) where last_name = 'GOMEZ'                          ✔ usa
b) where last_name = 'GOMEZ' and first_name = 'SELENA' ✔ usa
c) where first_name = 'SELENA'                        ✘ no (falta el nivel 1)
d) where last_name like 'GO%'                         ✔ usa (rango)
e) where last_name like '%EZ'                         ✘ no (comodín al inicio)
f) where upper(last_name) = 'GOMEZ'                   ✘ no (función sobre la columna)
Se necesita buscar "camiseta roja algodón" dentro de descripciones de 2.000 caracteres. ¿Qué índice? extra
FULLTEXT (índice invertido): create fulltext index idx_prod_desc on productos(descripcion); y consultar con match(descripcion) against('camiseta roja algodón'). like '%roja%' haría full scan.
Verdadero o falso: "Entre más índices tenga una tabla, más rápida es". extra
Falso. Las lecturas pueden mejorar, pero cada insert/update/delete debe actualizar (y rebalancear) cada árbol. Índices innecesarios o duplicados solo cuestan.
¿Qué diferencia a UNIQUE de PRIMARY KEY? extra
Ambos impiden duplicados, pero UNIQUE permite NULL y puede haber varios por tabla; la PK no admite NULL y hay solo una.

Clase 16Optimización y planes de ejecución

Plan de ejecución: el "paso a paso" que el DBMS sigue para ejecutar una sentencia SQL. Analogía: Waze busca la ruta más óptima; el plan de ejecución muestra la ruta actual para ver qué se puede mejorar.

Todas las cláusulas consumen CPU y memoria: select (mostrar), from (buscar), join (relacionar), where (filtrar), group by (agrupar), having (filtrar tras agrupar), order by (ordenar). Una consulta lenta puede tumbar todo el sistema.

EXPLAIN vs ANALYZE

EXPLAIN — dice lo que el DBMS "cree" que va a pasar. No ejecuta la sentencia; usa estadísticas internas. Ideal para consultas pesadas que podrían tumbar el sistema.
ANALYZE — dice lo que realmente pasó. Sí ejecuta la sentencia y muestra columnas extra r_rows, r_filtered (valores reales).

EXPLAIN informa: tablas involucradas, tipo de escaneo (índice o full scan), filas estimadas por tabla, uso de joins, etc.

Cómo leer las columnas de EXPLAIN

ColumnaSignificado
tableTabla que se lee en ese paso (el orden de las filas = orden del join)
typeMétodo de acceso. De mejor a peor: const (1 fila por PK/unique) → eq_ref → ref (índice no único) → range (rango en índice) → index (recorre todo el índice) → ALL (full scan)
possible_keysÍndices que podría usar
keyÍndice que realmente eligió (NULL = ninguno)
key_lenBytes del índice usados
refCon qué se compara el índice (const, otra columna...)
rowsFilas estimadas a recorrer (¡clave!)
ExtraUsing where, Using index (cubriente), Using index condition, Using filesort (ordenamiento extra), Using temporary, Impossible WHERE

Ejercicios de clase resueltos (BD world)

Patrón clave del profesor: aplicar una función (upper, cast, concat, year, date…) sobre una columna indexada en el where obliga al DBMS a calcularla en cada fila → full scan. Solución: dejar la columna "limpia" y transformar el valor constante.
Ej. 1 – where upper(Code) = 'AFG' diapositiva 
-- Mal: type=ALL (la función anula el índice PRIMARY)
select * from countries where upper(Code) = 'AFG';
-- Bien: type=const, rows=1
select * from countries where Code = 'AFG';
El collation por defecto (_ci) ya es insensible a mayúsculas, así que upper() sobra. Si hiciera falta, se normaliza el dato al insertar, no al consultar.
Ej. 2 – where cast(independence_year as integer) > 1980 diapositiva 
select code, name, independence_year
from   countries
where  independence_year > 1980;
create index idx_coun_inye on countries(independence_year);  -- type=range
El campo ya es numérico; el cast no aporta nada y bloquea el índice. Si el campo fuera texto, la solución real es corregir el tipo de dato de la columna (optimización a nivel de diseño).
Ej. 3 – where concat(continent,'-',region) = 'North America-Caribbean' diapositiva 
select * from countries
where continent = 'North America' and region = 'Caribbean';
create index idx_coun_cont_regi on countries(continent, region);
Ej. 4 – where surface_area > 5000000 diapositiva 
create index idx_coun_suar on countries(surface_area) using btree;
-- antes: type=ALL ~239 filas; después: type=range, pocas filas
La consulta está bien escrita; lo que falta es un índice BTREE (rango → no sirve HASH). Además, cambiar * por las columnas necesarias. Como la tabla es pequeña (239), la ganancia real es mínima: es la discusión "revista de 10 páginas".
Ej. 5 – Plan con y sin índice de los ejercicios de la clase anterior diapositiva
Correr explain antes y después de crear cada índice del Ej. 5-6 de índices. Debes ver: type pasa de ALL a ref/range, key pasa de NULL al nombre del índice, rows baja de ~15 M a una fracción, y en el count(*) aparece Using index (índice cubriente).
Ej. 6 – where country_id='COL' order by name, population diapositiva 
select name, district, population      -- no *
from   cities
where  country_id = 'COL'
order by name, population;
create index idx_citi_coid_name_popu on cities(country_id, name, population);
Sin el índice compuesto, EXPLAIN muestra Using filesort (ordenamiento extra). Con (country_id, name, population) las filas ya salen ordenadas del índice. Y preguntarse: ¿el order by es realmente necesario?
Ej. 7 – group by / having / order by en countries_languages diapositiva 
-- Original: errores lógicos
select id, count(language_id) as total_languages   -- "id" no está en el group by
from countries_languages
group by country_id
having count(language_id) > 0                      -- siempre se cumple: sobra
order by count(language_id) desc;

-- Mejorada
select   country_id, count(*) as total_languages
from     countries_languages
group by country_id
order by total_languages desc;
Problemas: (1) selecciona id pero agrupa por country_id (resultado indeterminado); (2) el having > 0 es inútil porque todo grupo tiene al menos 1 fila; (3) recalcula el count en el order by; usar el alias. Un índice en country_id permite agrupar sin tabla temporal.
Ej. 8 – where id = 'COL' or id = 'USA' diapositiva 
select * from countries where id in ('COL','USA');
Funcionalmente igual; IN es más legible y el optimizador lo resuelve como range sobre la PK (2 filas). Los OR sobre columnas distintas son los que suelen romper el uso de índices. Y de nuevo: evitar *.

Práctica extra (estilo profesor)

select * from compras where year(fecha) = 2023; — ¿cómo mejorarla? extra 
select id, total from compras
where fecha >= '2023-01-01' and fecha < '2024-01-01';   -- + índice btree en fecha
select * from clientes where substring(documento,1,3) = '100'; extra 
select ... from clientes where documento like '100%';   -- prefijo: sí usa índice
select * from productos where precio * 1.19 > 119000; extra 
select ... from productos where precio > 100000;   -- se despeja la constante
select * from usuarios where lower(email) like '%@gmail.com'; extra
Dos problemas: función sobre la columna y comodín al inicio. Ninguna versión con %... al inicio usa índice. Opciones: guardar el dominio en una columna aparte (email_dominio) indexada, o normalizar a minúsculas al insertar.
Un EXPLAIN muestra type=ALL, rows=12000000, key=NULL. ¿Qué significa y qué haces? extra
Full scan de 12 M filas sin índice. Revisar: ¿hay índice sobre la columna del where? ¿se le aplica una función? ¿hay like '%x'? ¿la condición tiene buena selectividad? Crear el índice correcto y validar con EXPLAIN que pase a ref/range.
¿Por qué usarías EXPLAIN y no ANALYZE en producción para un DELETE masivo? extra
Porque ANALYZE ejecuta la sentencia: borraría los datos de verdad y podría bloquear tablas. EXPLAIN solo estima.

Clase 17Motores de almacenamiento

Motor de almacenamiento: componentes que gestionan cómo se guardan los datos y cómo se accede a ellos. Dos tablas iguales pueden comportarse distinto solo por tener motores diferentes.
Analogía: los motores son a las tablas lo que los sistemas de archivos (FAT32, ext4, NTFS) son a un disco.

Respuesta corta: depende de la necesidad (transaccionalidad, lecturas vs escrituras, crecimiento, medio físico, número de usuarios…).

  • La latencia de red importa si se usan motores que se conectan a BD externas.
  • La memoria no es infinita: Memory es rapidísimo… hasta que colapsa.

Ej. 2 – Procedimiento pr_fill(p_table_name, p_records) diapositiva 
delimiter //
create procedure pr_fill(in p_table_name varchar(30), in p_records bigint unsigned)
begin
  declare i bigint unsigned default 1;
  declare v_value real;

  -- nombre de tabla dinámico → SQL dinámico
  set @sql = concat('insert into ', p_table_name,
                    ' (my_id, my_date, my_value, my_value_type, my_description)',
                    ' values (?, ?, ?, ?, ?)');
  prepare stmt from @sql;

  while i <= p_records do
    set v_value = floor(rand() * 10000);                            -- 0..9999
    set @p_id   = i;
    set @p_date = date_add('2000-01-01',
                  interval floor(rand() * datediff('2050-12-31','2000-01-01')) day);
    set @p_val  = v_value;
    set @p_type = if(mod(v_value, 2) = 0, 'EVEN', 'ODD');
    set @p_desc = md5(uuid());                                      -- 32 caracteres
    execute stmt using @p_id, @p_date, @p_val, @p_type, @p_desc;
    set i = i + 1;
  end while;

  deallocate prepare stmt;
end //
delimiter ;

-- Versión alternativa en UNA sola sentencia con el motor sequence (mucho más rápida)
delimiter //
create procedure pr_fill_seq(in p_table_name varchar(30), in p_records bigint unsigned)
begin
  set @sql = concat(
    'insert into ', p_table_name,
    ' select seq, date_add(''2000-01-01'', interval floor(rand()*18627) day), v,',
    ' if(mod(v,2)=0,''EVEN'',''ODD''), md5(uuid())',
    ' from (select seq, floor(rand()*10000) v from seq_1_to_', p_records, ') s');
  prepare stmt from @sql; execute stmt; deallocate prepare stmt;
end //
delimiter ;

-- Uso (¡dentro de una transacción!)
start transaction;
call pr_fill('t_innodb', 10);
commit;
Puntos que el profesor revisa: SQL dinámico con prepare/execute (no se puede usar una variable como nombre de tabla directamente), my_value_type calculado a partir de my_value con mod, texto de 32 caracteres con md5(uuid()), y transacción alrededor de la llamada.
Ej. 3 – Procedimiento pr_clear(p_table_name, out p_records) diapositiva 
delimiter //
create procedure pr_clear(in p_table_name varchar(30), out p_records bigint unsigned)
begin
  set @sql = concat('delete from ', p_table_name);
  prepare stmt from @sql;
  execute stmt;
  set p_records = row_count();     -- filas afectadas por el último DML
  deallocate prepare stmt;
end //
delimiter ;

commit;
select @borrados;
Se usa delete y no truncate porque truncate no informa filas afectadas (y es DDL: hace commit implícito).

Ej. 8 – Conclusiones esperadas diapositiva
  • Más rápido para insertar: blackhole (no guarda nada), luego Memory (RAM). Entre los que persisten, MyISAM/Aria suelen ganar en inserción masiva sin concurrencia; InnoDB rinde bien si se usa una transacción (sin ella hace commit por cada fila → horas).
  • Más rápido para borrar: blackhole (0 filas), luego Memory.
  • Más rápido para consultar: Memory; luego Aria/MyISAM (optimizados para lectura). CSV es el más lento (sin índices, texto plano). Sin índices todos hacen full scan.
  • Error de Memory con muchos registros: The table 't_memory' is full — la tabla supera max_heap_table_size (por defecto 16 MB). La RAM no es infinita.
  • Blackhole: tiempos ~0 y count(*) = 0 porque descarta todo lo que se inserta; solo existe la estructura.

Clase 18Particionamiento

Particionar: dividir una tabla en segmentos más pequeños (como un disco duro). A nivel lógico sigue siendo una sola tabla; a nivel físico son varios archivos separados.

¿Para qué?

  • Reducir lecturas/escrituras en tablas muy grandes (mejor velocidad).
  • Menor probabilidad de pérdida de información si se daña un archivo.
  • Facilita eliminar datos antiguos o archivados (drop partition).
  • Mal usado no mejora… empeora (igual que los índices).
Lo importante no es memorizar los tipos, sino saber cuándo usar cuál. Procurar que el tipo de partición coincida con las búsquedas más frecuentes (minimiza lecturas en disco).

Tipos

TipoCómo funcionaCuándo usarlo
RANGEExpresión que retorna un valor; según el rango cae en una partición. Admite maxvalue.Tiempos o fechas (históricos, auditorías, logs)
LISTValores fijos por partición (el campo no tiene que ser ENUM)Lista corta de categorías conocidas
HASHN particiones; expresión % N (expresión entera)Distribución uniforme
LINEAR HASHComo hash, con potencias/logaritmosMejor si habrá que redistribuir particiones a futuro
KEYEl DBMS calcula el hash internamente sobre uno o varios camposSin criterio claro / solo distribuir carga
-- RANGE con maxvalue
create table singers(
  id int not null, first_name varchar(50), last_name varchar(50),
  birth_date date, gender enum('F','M','LGBTIQ+'),
  primary key(id)
)
partition by range(year(birth_date)) (
  partition p_2020 values less than (2020),
  partition p_2022 values less than (2022),
  partition p_2024 values less than (2024),
  partition p_9999 values less than maxvalue
);

-- LIST
partition by list(gender) (
  partition p_woman values in ('F'),
  partition p_man   values in ('M'),
  partition p_lgbtiq values in ('LGBTIQ+')
);

-- HASH
partition by hash(month(birth_date)) partitions 3;
-- birth_date='1992-07-22' → month=7 → 7 % 3 = 1 → partición p1

-- LINEAR HASH / KEY
partition by linear hash(month(birth_date)) partitions 3;
partition by linear key(first_name) partitions 3;
Cálculo HASH (pregunta típica): partición = expresión MOD número_de_particiones, numeradas desde p0. Ej.: hash(month(fecha)) partitions 4 con fecha '2024-11-03' → 11 % 4 = 3 → p3.

Comandos

CasoComando
Particionar tabla existentealter table singers partition by range(year(birth_date)) (partition p_2020 values less than (2020), ...);
Agregar particionesalter table singers add partition (partition p_2027 values less than (2027));
Reducir particiones (hash/key)alter table singers coalesce partition 2; → de 6 quedan 4
Quitar particionamientoalter table singers remove partitioning;
Modificar rangoalter table singers reorganize partition p_2020 into (partition p_2020 values less than (2005));
Eliminar una partición (y sus datos)alter table singers drop partition p_2020;
Partir una particiónalter table singers reorganize partition p_01 into (partition p_01_a values less than (2010), partition p_01_b values less than (2012));
Unificar particionesalter table singers reorganize partition p_01_a, p_01_b into (partition p_01 ...);
Importante: máximo 1024 particiones por tabla en MariaDB (más particiones ≠ mejor rendimiento). Modificar particiones en una tabla grande en producción es muy costoso (bloqueos, concurrencia).
Fórmula para un EXCELENTE rendimiento: índices óptimos + motores acordes a su función + particiones adecuadas + buen diseño backend/DBMS (concurrencia) + principio del mínimo privilegio + límites de ejecución por usuario.

Ej. 2 y 6 – Archivos generados diapositiva
Tras particionar, cada partición tiene sus propios archivos de datos, con el patrón tabla#P#particion:
  • InnoDB: t_innodb#P#p_odd.ibd, t_innodb#P#p_even.ibd
  • MyISAM: .MYD + .MYI por partición
  • Aria: .MAD + .MAI por partición (4 pares en t_aria)
  • Memory/Blackhole: no generan archivos de datos (solo cambia la definición)
  • Puede aparecer un .par con la definición de particiones (versiones antiguas)
Al hacer remove partitioning vuelven a un único archivo de datos. La suma del tamaño de las particiones suele ser algo mayor que el original (overhead por archivo).
Ej. 3–4 – ODD/EVEN y rango de id, con particiones diapositiva
La consulta por my_value_type en tablas particionadas por LIST de ese mismo campo mejora: el DBMS hace partition pruning (solo lee una partición; se ve en explain partitions / columna partitions). La consulta por my_id between … no mejora (puede empeorar), porque ninguna tabla está particionada por id: tiene que leer todas las particiones.
Ej. 5 – Contar, eliminar una partición, volver a contar diapositiva 
select count(*) from t_aria;
alter table t_aria drop partition p_2010;
select count(*) from t_aria;   -- bajó: los datos de esa partición se borraron
Conclusión: drop partition elimina datos de forma casi instantánea (borra un archivo) — es la forma eficiente de purgar históricos, mucho más rápido que un delete.
Ej. 7 – Conclusiones diapositiva
  • Mejora solo cuando el filtro de la consulta coincide con el criterio de partición.
  • CSV no soporta particionamiento.
  • Las tablas que más rápido crean particiones son las sin datos reales (blackhole) o en RAM (memory).
  • Particionar reescribe toda la tabla: en tablas grandes es costoso.

Clase 19Eventos

Evento: sentencia SQL o PL/SQL programada para ejecutarse automáticamente: periódicamente, una única vez en un horario predefinido, o en un rango de tiempo. "Código SQL que se ejecuta de forma autónoma". Analogía: crontab / tarea programada / job.

Tipos — responde: ¿Cuándo? ¿Cada cuánto? ¿Hasta cuándo?

TipoDescripciónEjemplo / caso de uso
PeriódicoIndefinido, intervalos de segundos a añosDepurar registros de más de 10 años · logs, métricas
Única ejecución / programadoUna sola vez en un momento dadoA las 2:00 am de mañana limpiar datos · migraciones
Rango de tiempoPeriódico entre starts y endsAplicar descuentos diarios por un mes · campañas, promociones
-- Requisito: activar el planificador (root o usuario con permisos)
SET GLOBAL event_scheduler = ON;      -- sin esto, los eventos "no existen"

-- Op 1: periódico indefinido
create event ev_periodic_event
  on schedule every 1 day
  on completion preserve            -- o "not preserve"
  do
    update some_table set some_field = 'SOME_VALUE' where id > 100;

-- Op 2: única vez (3 horas después de crearlo)
create event ev_scheduled_event
  on schedule at current_timestamp + interval 3 hour
  on completion preserve
  do
    update some_table set some_field = 'SOME_VALUE' where id > 100;

-- Op 3: rango (cada minuto, desde +10 s, durante 15 min)
create event ev_range
  on schedule every 1 minute
  starts current_timestamp + interval 10 second
  ends   current_timestamp + interval 900 second
  on completion preserve
  do
    update some_table set some_field = 'SOME_VALUE' where id > 100;

-- Administrar
drop event ev_range;
alter event ev_range enable;
alter event ev_range disable;
alter event ev_periodic_event on schedule every 30 day on completion preserve do (...);
show events;
on completion preserve / not preserve: al terminar (evento único ejecutado o rango vencido), preserve deja el evento definido (deshabilitado); not preserve (por defecto) lo elimina automáticamente.

¿Qué tener en cuenta?

  • Con timestamp no se puede superar 2038-01-19 05:14:07.
  • Como los triggers, los eventos no retornan nada.
  • Los eventos no pueden crear/modificar/eliminar funciones, procedimientos ni triggers.
  • Los eventos no pueden ser creados/modificados/eliminados desde una función, procedimiento o trigger.
  • Mejor práctica de diseño: crear un procedimiento (PR) con la lógica y que el evento solo haga call → reutilizable, probable y mantenible (opción 2 de la discusión).

Pros y contras

✅No se necesitan scripts externos para automatizar
✅Independientes del sistema operativo
✅Pueden usar funciones y procedimientos personalizados
✅ / ❌No ejecutan código externo (scripts, web services): bueno por seguridad, malo como limitación
✅Ejecución 100% en el servidor, 0% en los clientes
❌Un único hilo para todos los eventos → muchos eventos pesados = cuello de botella
Los eventos consumen CPU. Como DBA, revisa que no haya eventos innecesarios activos; eventos mal diseñados o a la misma hora consumen CPU silenciosamente.

¿Por qué no programar 10 eventos pesados a las 00:00? extra
Hay un único hilo para eventos: se encolan, compiten por CPU y bloqueos, y generan un cuello de botella. Hay que escalonar horarios.
¿Puede un trigger crear un evento? ¿Puede un evento crear un procedimiento? extra
No y no. Los eventos no se crean desde funciones/procedimientos/triggers, y los eventos no pueden crear/modificar/eliminar funciones, procedimientos ni triggers.
